PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

PAM (Project Agentic Management) does two things. First, it lets a team share an agentic configuration: you run pam init in a repository, the way you run git init, and it writes a committed .pam/ that defines the team and its org chart, the skills the agents can use, and a shared knowledge base. That config travels with the repository and is useful on its own, so anyone who clones the repo inherits the same setup. Second, it lets a developer activate and employ that configuration: pam activate works like a Python virtualenv, switching you into a project and loading its per-developer auth from a local vault so skills run and the forge connects across systems like GitHub, GitLab, and Jira. From there cmux runs a fleet of agents, giving each its own home directory, and the worker at the center of the fleet is ADA, the Atomic Development Agent, which carries one issue to a reviewed pull request and then stops. A Runtime watches the forge and turns events into work for agents that already exist. One tool, pam, carries all of it.

Overview

A lot of teams now face the same question: how do several people direct a fleet of coding agents on the same codebase without each person wiring it up by hand. PAM answers it in two halves. The first half is a way to share an agentic configuration, so a team agrees on it once and commits it. The second half is a way for each developer to activate and employ that configuration on their own machine, so the shared setup actually runs. Figure 1 stacks the two halves and the pieces inside them.

The top layer is the shared half. The three below it are the employed half, which turns that shared config into running agents on one developer's machine. The rest of this note walks the stack top to bottom: what a team shares, how a developer activates it, how the fleet runs, the ADA worker at the center, and the Forge and Runtime that feed it.

One tool

There is a single command surface, pam, and installing it sets up the whole system; there is no separate system init. ADA ships inside it, under pam/agents/ada/, because ADA only means something once a project binds its placeholders, so it is part of PAM rather than a separate install. A developer who only wants the atomic agent uses the ADA parts; a team running a fleet uses the rest.

What PAM adds

PAM is a handful of novel pieces that fit together:

  1. pam init creates a committed .pam/ of shared agentic definitions for a repo: the skills, a knowledge base, the team's org, and the agent roles.
  2. ADA, the Atomic Development Agent, which runs an Oracle to keep it from idling or stopping prematurely and a per-agent queue, cq, to track its own work.
  3. pam activate activates a repo the way a Python virtualenv does, loading the per-Project environment and auth a project's skills need (the vault).
  4. cmux spins up and coordinates fleets of agents.
  5. a Runtime, comparable to GitHub Actions and workflows, that agents subscribe to so forge events trigger agentic actions and work.
  6. a knowledge base agents read from before a task and write back to after.

Philosophy

A few principles hold the design together, carried from the practice that produced ADA. An agent owns one unit of work and carries it whole, from the issue to a reviewed pull request. Progress is not monotonic: a rebase un-does a test that passed and a moving base un-does a green build, so an agent reports its position against a specific commit rather than claiming something is simply done. Silence is indistinguishable from finished, so before an agent goes quiet it says what it did, what it could not verify, and what is now blocked and on whom. An honest gap beats a confident wrong claim, because an honest gap costs an hour while a confident wrong claim costs a week and is repeated by everyone downstream. Two structural principles sit underneath those. State is split the way git splits it: authored configuration is shared in the repository, and recorded state stays on each machine, so no stale cache of the authored half can drift from the truth. And documentation stays in sync with code: a change to how the system behaves and the documentation that describes it land together, because an agent that reads a stale document acts on it. The aim of all of this is that one person can trust the work of many agents at once.

Sharing a configuration

The first half of PAM is a shared configuration that lives in the repository. You start it by running pam init in a repo, the way you run git init, which creates .pam/ there and registers the Project in your local store. A Project is the container: a git repository plus its .pam/. It is what you pam init, and it can reference more than one repository; Open Library is one Project over five. The repository is where a Project is rooted, not what a Project is. (pam init and the .pam/ layout are shipped.)

What .pam/ holds is the team's agreement about how agents work this codebase: the roles and the org chart in project.toml, the standalone-readable role catalog in roles.md, the team definitions under agents/, the skills the agents may use, and a shared knowledge base under kb/. It is committed and shared like tracked files, and it is valuable on its own: someone who never runs pam still gets the standardized roles, the ADA process, and the knowledge base just by reading the repo. Clone the repo and you have the setup.

PAM splits its state the way git does. The authored half lives in the repository and is shared through commits; the recorded, per-developer half stays on each machine, like ~/.gitconfig against tracked files. Figure 2 shows the split.

On your machine, ~/.pam/ holds the Store, a single SQLite database (pam.db) that records your Projects, your agents, their memberships and roles, the Epics, and each agent's phase, plus the per-developer settings written by pam activate. A teammate who clones the repository gets the setup and none of your running state. (The Store, agents, memberships, roles, and Epics are shipped.)

The knowledge base

The knowledge base is a Project-level shared store of what the team has learned, for humans and agents alike. An agent reads it before a task and writes back to it after, and every agent contributes, so a lesson learned once does not have to be learned again. It is not a separate step: pam init seeds .pam/kb/ for you, Obsidian-style, as plain markdown notes linked with wikilinks, the [[note]] style, so it reads for a person and an agent alike and needs no special tooling. It is committed with the rest of .pam/. Open Library's is ol-kb. (The seeded .pam/kb/ is shipped; a richer first-class knowledge base is tracked on #34.)

Activating a configuration

The second half of PAM is how a developer picks up that shared config and runs it. Cloning the repo gives you the setup; it does not give you a running fleet, because running agents need an identity, auth, and somewhere to live, and none of that belongs in the repo. pam activate supplies it, and it works like a Python virtualenv: in any repo that has a .pam/ it switches you into that Project and makes it the active one for your shell, the way activate switches you into a virtualenv.

Activating sets who you are for this Project on this machine. It records your per-developer settings under ~/.pam/projects/<project>/ and never stores credentials in the repo or the Store: instead it points your forge client at a per-Project auth directory, so you authenticate once, as the Project's bot, and from then on every forge and git action runs as that identity. This per-developer, per-Project store of environment and auth is the PAM vault: it lives under ~/.pam/projects/<project>/, is never committed, and is what makes the shared skills actually work and the forge actually connect, across systems like GitHub, GitLab, and Jira. pam status shows the active Project and pam deactivate clears it, exactly as a virtualenv would. (pam activate, the per-developer per-Project env, and the virtualenv-style shell activation are shipped.)

Prior art. Per-directory activation that loads environment on entry is a known pattern: direnv loads and unloads environment variables by directory, and mise manages per-project tools and environment. PAM adds the agentic layer on top, the identity, auth, and fleet a project's agents need, and may build on direnv or mise for the environment half in the future rather than carrying its own.

Activating gets you an identity and auth for the Project; running the fleet is the next section.

Fleet orchestration

With a Project activated, a fleet of agents runs on your machine. Two tools bring the fleet up and hold it together: cmux, for persistent sessions and workspaces, and claudio, the Claude Code wrapper where each agent's home directory lives. Each agent keeps its own local queue, cq, and talks to its peers through Claude's native SendMessage.

cmux

cmux, the Claude multiplexer, provides persistent, re-attachable sessions and keeps agents alive, organized into workspaces, each agent in its own home directory (hosted by claudio, below). pam spawn seeds an onboarded agent's home with a bootstrap that points at its committed definition in .pam/agents/<name>/ and the repo, then brings it up through cmux so the agent boots clean and reads its own identity, with the active Project's env applied so it acts as the Project bot. An ADA agent creates its own worktree as its first act; a lead just works the forge.

The integration runs one way on purpose: cmux integrates with PAM, and PAM never imports cmux, so pip install pam works on a machine with no tmux and a test keeps that rule green. The Runtime's decision core is tmux-free and runs in dry-run by default; real dispatch goes through the cmux seam. (pam spawn is shipped as a dry-run-by-default prototype; a first-class setup seam in cmux is the clean follow-up, tracked on #50.)

claudio

claudio wraps Claude Code with programmable logic, and it is where an agent's home directory lives: its identity, its cq queue, and its Claude session. cmux brings agents up through claudio, which exposes the stop hook that the Oracle augments (Section V), so the subconscious check runs at exactly the moment an agent is about to go quiet. Where the earlier ADA system also used claudio for an agent-to-agent inbox, PAM now leaves that to Claude's native SendMessage.

cq, the per-agent queue

cq is an agent's own issue queue, one small SQLite tracker per agent for the work it is tracking for itself, kept in the agent's home under ~/.pam/. It holds the agent's own tasks, blockers, and side-discoveries, and it is also the default local tracking system when the repository's remote does not imply a forge. (The agent home is shipped; folding cq into PAM and using it as the default tracker is forward-looking.)

Messaging

Agents talk to each other through Claude's native SendMessage, which delivers a message to the target agent and is picked up when that agent next comes idle, so a long-running agent is never interrupted mid-task. Reporting lines in the org chart are organizational labels, not a live routing path; PAM does not relay work from agent to agent through many hops.

ADA and the Oracle

ADA is the core of PAM, the agent that does the work and the worker at the center of the fleet. It owns a single issue and the pull request that resolves it, as a pair, and runs a disciplined process over that pair. The method, taken from the versions that already work in practice, is below; Figure 3 shows the same flow at a glance.

  1. Own the pair. ADA takes one issue and the pull request that resolves it as a single unit of work, and carries it whole.
  2. Post a ledger. One line for each thing that must become true, written in the issue's own terms as a behaviour rather than a task. reported against a specific commit, never as a bare percentage
  3. Develop red-first. In its own worktree, write a failing test and watch it fail for the right reason before making it pass; a regression test before every fix.
  4. Open a draft PR early. The work is visible while it is still in progress. draft PR + CI, from the first commit
  5. Verify in the real environment. Not the same as the suite passing; sort every claim into what was actually run and what was only read.
  6. Get an adversarial review. A subagent that inherits none of ADA's context reviews the work before it is marked ready.
  7. The Oracle checks. As ADA is about to stop, its subconscious surfaces at most one thing it may have missed. silence is not approval
  8. Human review and merge. ADA never merges. This is the one line automation never crosses.

The one rule that defends against the two failure modes that matter is when ADA may stop. Finished means it closed its own ledger and the only thing left is a human merge. Blocked means a decision, authorization, or access it searched for first and could not resolve. Everything else is still work, so it keeps going. That rule is what prevents an agent from idling for days waiting on a human, and from being poked by a schedule to do low-value work when nothing is left.

The Oracle. The Oracle augments the agent's stop hook and prevents premature idling. It is a subconscious, not a supervisor: it does not drive the agent or approve it. When the agent is about to stop, the Oracle surfaces at most one thing it may have missed, for example tests written for code that was never actually run, and the agent decides what to do with it. Its silence is not approval, because nothing firing includes the case where nothing could fire, so a check that stayed quiet and a check that could not run look the same.

The Forge

The Forge is what powers a Project's work: the systems where issues and pull requests live. It is an umbrella over two configurable systems, a project tracking system, where Issues and Epics live, and a development system, where pull requests and review live. At a minimum a Project needs these two, Issues and PRs.

The two systems are configured separately, and they can be one product or two. GitHub does both, so one product can cover the Forge. Or they can differ, for example Jira for Issues and GitHub for pull requests. Tracking system examples are Jira and GitHub Issues; when the repository's remote does not imply a forge, PAM falls back to local cq as the default tracker. Development system examples are GitHub, GitLab, and Gerrit. An ADA agent owns an Issue in the tracking system and a PR in the development system as a pair, so one unit of work spans both. Figure 4 shows the two systems side by side.

Epics

An Epic is a unit of work inside a Project: a bundle of issues, the thing an operator manages day to day. Epics and their issues live in the tracking system, and a Division Lead owns and manages an Epic. In a GitHub-backed Project an Epic is projected onto an epic issue, with its pieces as sub-issues; the epic issue is how the Epic appears in that system, and the concept is the unit of work itself. (Epics and their membership are shipped; pam epic add, assign, and state run today.)

Docs-first note. The two-system split is the intended model. The shipped schema has a single tracker field plus repos, and the forge adapter reads GitHub signals today. Splitting the configuration into a tracking system and a development system, and the local-cq default, are filed on #35 so the code reconciles to the model. A Project does not have to build its adapters from scratch either: the intended model lets it fetch what it needs as Forge plugins from a registry, for example a GitHub, Jira, or GitLab plugin. The registry is forward-looking; sharing a Project today is cloning its repository.

The Runtime

The Runtime is the event watcher for the Forge, similar in spirit to the GitHub Actions API, with one difference that is the reason PAM exists: it can keep a durable agent alive across many events. It polls the tracking system for work and reads pull-request and CI state from the development system, decides what is actionable, and dispatches to an agent that already exists rather than starting a fresh container each time. Its plugins are Actions: a trigger (an event or a schedule) plus a handler (deliver to an agent, spawn one, run a skill, or run a script).

The Runtime fires an Action once per material change, not once per poll, so a pull request open for days triggers its Action once rather than every minute. It does this with a dedup key over the signals an Action cares about and a per-Action cooldown. (The decision core, with dedup, cooldown, and a dispatch interface, runs today in dry-run. The poll loop and live, health-gated dispatch are the next build step, tracked on #21.) Figure 5 shows the event-to-action cycle.

The arrow from the Runtime to the tracking system runs outward on purpose: the Runtime polls, pulling changes on its own schedule, and the results come back on the same request. The direction could be reversed only if those systems pushed events, through webhooks or a workflow, but then a durable, long-lived agent would have nothing holding it to receive them, and you would not need the Runtime at all. PAM polls precisely because a persistent agent cannot depend on a remote system reaching it. That is the same reason an ephemeral runner does not fit this work: a stock run gets a container, does a thing, and is destroyed, while an ADA agent must survive from the moment a PR opens until it merges, holding a worktree and accumulated context.

The team and roles

A Project is worked by a team, also called the fleet: the agents staffed on it. The team and its org chart are part of the shared config in .pam/, so a teammate who clones the repo inherits the same roster and reporting lines. An agent is first-class and independent of any one Project, and it joins a Project through a membership that gives it a role and a reporting line. PAM ships four roles, kept distinct on purpose.

ADA, the Atomic Development Agent

The ada_agent role is ADA, the agent that does the work: it owns one issue and its pull request, and runs the disciplined process described in Section IV. It is the worker every other role exists to feed and unblock.

Division Leads

A Division Lead (division_lead) manages Epics. The Lead owns a set of Epics, breaks them into issues for ADA agents, and unblocks those agents as a consultant. Reporting is organizational, not an execution path: the reporting edge is an org-chart label, and PAM does not route live work from agent to agent through many hops.

Project Lead

The Project Lead (project_lead) is a meta role. It owns the Project itself: it keeps the Project's documentation current and unblocks Division Leads where it can. It tends the shared setup rather than any single Epic.

Generic

The generic role (agent) is the catch-all for a team member that is not one of the above, so a Project can staff a role PAM does not name without inventing a type.

Note. These four are the shipped seed roles (project_lead, division_lead, ada_agent, agent), and the paper keeps the two lead roles distinct rather than collapsing them into one. A Project can define its own roles on top of these.

Where context lives

It also helps to see the pieces as channels: where each kind of context lives, who can see it, and how agents and humans pass information. The center of gravity is .pam/, the committed brain of the Project, so every agent that boots in the repo starts from the same place. Around it sit the per-agent and live channels. The knowledge base straddles both: it is committed in .pam/, and it is the one shared channel every agent both reads and writes, so a lesson learned once does not have to be learned again.

Using PAM

The pam command line

The command line manages the Project and the team. It is structured as pam <noun> <verb>: a Project, an agent, a membership, an Epic. The flow below runs today. You make a repository agent-workable, activate it as your Project for this machine, register the people who work it, define an Epic, put an agent on a piece of it, spawn the fleet, and read state back.

cd ~/Projects/openlibrary
pam init                          # create .pam/ here; register the Project in ~/.pam

pam activate openlibrary --as openlibrary-bot    # per-developer identity, virtualenv-style
GH_CONFIG_DIR=~/.pam/projects/openlibrary/gh gh auth login   # authenticate once, as the project bot

pam agent onboard ol-lead   --project openlibrary --role project_lead
pam agent onboard tags-lead --project openlibrary --role division_lead --reports-to ol-lead
pam agent onboard ada-13842 --project openlibrary --role ada_agent     --reports-to tags-lead

pam epic add "Tags" --project openlibrary --lead tags-lead --epic 13755 --year 2026
pam epic assign "Tags" --agent ada-13842 --sub 13842 --by tags-lead

pam spawn ada-13842 --project openlibrary        # seed the agent home, bring it up via cmux (dry-run)
pam spawn ada-13842 --project openlibrary --go   # actually launch

pam status                        # your Projects and their leads
pam team --project openlibrary    # the reporting tree with statuses
pam agent state ada-13842         # computed work state from pull-request and CI signals
pam agent ledger ada-13842        # per-requirement ledger: done / stale / asserted / open vs HEAD
pam epic state "Tags"             # the epic rollup and each agent's state

What happens at each step

  1. init makes the repo agent-workable: it writes .pam/, infers the forge from the origin remote, seeds the role catalog and the knowledge base, and registers the Project in your ~/.pam. Commit .pam/ with the code.
  2. activate makes you the Project bot on this machine: it writes your vault and points the forge client at a per-Project auth dir, so you authenticate once and every later action runs as that identity.
  3. onboard registers the team, a Project Lead, a Division Lead, and ADA workers, each with a role and a reporting line, writing a committed definition into .pam/agents/.
  4. epic add / assign defines a unit of work and puts a named ADA agent on one of its sub-issues.
  5. spawn brings an agent up through cmux and claudio in its own home, with the vault applied; an ADA agent worktrees itself and begins, reading the knowledge base first.
  6. status / team / state / ledger read live signals back and report each agent's position against the current commit, never as a bare percentage.

A name that is already live cannot be onboarded again, because reusing a name must never merge two agents' histories; retire the old one first with pam agent retire. The state commands read live pull-request, CI, and ledger signals and report the position against the current commit, never as a bare percentage.

Case study: Open Library

Open Library is a large open-source library catalog maintained by a small staff, and it is the first project run as a PAM Project. Its earlier automation, ADA, is described in a companion paper [1]; PAM generalizes that work so any team can adopt it. As a Project, Open Library uses GitHub for both the tracking system and the development system, so one product covers the Forge. Table 2 is its configuration at a glance. The whole shape comes straight from the two halves. The shared half is committed in the repo's .pam/: the roles, the org chart, the skills, and the shared knowledge base, ol-kb. Any maintainer who clones the repo inherits it. The employed half is each developer running pam activate to pick it up: a Project Lead tends the shared setup and the documentation, Division Leads own the epics, for example an import pipeline or an internationalization effort, and break them into issues, and ADA agents take those issues to reviewed pull requests, reading and writing ol-kb as they go. A human reviews and merges. This is the shape PAM is built to make ordinary: a small group of people directing a larger fleet of agents, each carrying one unit of work, with the configuration shared in the repository for anyone to pick up. (Open Library is the reference instance; the fuller write-up of its operation lives in the ADA paper and will grow here as the Project runs on PAM.)
