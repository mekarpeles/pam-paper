PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

PAM (Project Agentic Management) is one tool for running AI agents against real software projects. Its atomic unit is ADA, an agent that takes a single issue, develops it in an isolated git worktree against a ledger of what must become true, carries it to a pull request a human reviews and merges, and then stops. You make a repository agent-workable by running pam init in it, the way you run git init. For a team, PAM adds a management layer around a fleet of these agents. PAM splits its state the way git does: a Program's authored configuration lives in the repository under .pam/, committed and shared, while each developer's recorded state (agent homes, sessions, and a local SQLite Store) lives in ~/.pam/ and stays on their machine. Three layers sit on that split. The Store is the local recorded state. The Runtime watches a project's issues and pull requests and dispatches work to agents that are already running. The Program config in .pam/ is the authored setup. This paper describes the model, ADA's contract (in particular when an agent is finished, when it is blocked, and why that line is the crux), the three layers, and the constraints that shape them.

Overview

PAM is one tool, pam, for running AI agents against real projects. You run pam init in a repository the way you run git init, and that repository becomes agent-workable. Open Library is one such project. Lenny, Petabox, and PAM itself are others. Nothing in the core is specific to Open Library. A developer who only wants a single reliable agent uses ADA, the atomic unit. A team running a fleet uses the management layer around it.

The model

One tool, and ADA is the product. There is one command surface, pam, and installing it sets up the whole system. ADA ships inside it, at pam/agents/ada/, because ADA only means something once a project binds its placeholders, so it is a part of PAM and not a separate install. ADA is the broadly useful piece. Every development project needs an agent that can carry one unit of work to a quality pull request and then stop, while only some projects need a management layer over a fleet. So ADA is the product, and the Runtime is the input that feeds it.

The git-style state split. PAM splits its state the way git does, for the same reason. A Program's authored configuration lives in the repository under .pam/: the schema, the repositories, the issue tracker, the ADA setup, the roles, and the labels. It is committed and shared, like .git/config together with tracked files. A developer's recorded state lives in ~/.pam/: the agent home directories, their sessions, and the Store, which is a local SQLite database. It is per machine and never shared, like ~/.gitconfig. The cq work log and the identity files live there too, inside each agent's home. The authored half travels in the repository; the recorded half stays on the machine. A teammate who clones the repository gets the setup, not your running agents.

The three layers. Three layers sit on that split. The Store, in ~/.pam/, is the recorded state: which Programs you have, your agents, their memberships and roles, the projects, and each agent's phase. The Runtime is PAM's execution layer: it watches a Program's issues and pull requests and dispatches work to agents through Actions. The Program config, in the repository's .pam/, is the authored setup, reviewed through the same pull requests as the code. The rest of the paper takes ADA (§III) and then each layer in turn: the Store (§IV), the Runtime (§V), and the Program config (§VI).

ADA, the atomic unit

The contract. ADA owns one issue from end to end. It starts by posting a ledger: one line for each thing that must become true, written in the issue's own terms as a behavior rather than a task. It develops in its own worktree, writing a failing test first and watching it fail for the expected reason before making it pass, and it adds a regression test for every defect it hits, written before the fix. It opens a draft pull request early, so the work is visible while it is still in progress. It then tests in the real environment, which is not the same as the suite passing, and sorts every claim into what it ran and what it only read. Before marking the work ready it gets an adversarial review from a subagent that inherits none of its context, and every finding is either fixed with a test or rebutted with evidence. It never merges. A human does that.

The Oracle. ADA carries a verification layer called the Oracle, and the Oracle is a subconscious rather than a supervisor. It does not drive the agent or approve it. Its one job is to catch the moment the agent is about to stop having missed something, for example writing tests for code it never actually ran. It surfaces at most one thing at a time, and the agent decides what to do with it. Its silence is not approval: nothing firing includes the case where nothing could fire, so a hook that stayed quiet and a hook that could not run look the same.

Finished, blocked, or still working: the crux. The hardest part of the contract is knowing when to stop, and it is the crux of the whole design. An agent is finished only when it has closed its own ledger and the single remaining step is a human merge. It is blocked only when it needs a decision, an authorization, or an access that it searched for first and could not resolve, and it says so with a closed question: what it needs, the options, what it already checked, and who decides. Everything else is still work, so it keeps going. That line defends against the two failure modes that matter most: an agent that idles for days waiting on a human, and an agent that a schedule keeps poking into low-value work when nothing real is left.

The Store

The Store is the local SQLite database in ~/.pam/. It records Programs (each owns one or more repositories), agents (first-class and independent of any Program, each with a stable ULID id and a reusable display name), roles (a seedable catalog of definitions that carry permissions), and memberships (the binding that joins an agent to a Program with a role and a reporting line). A role and a membership are different: the role is the definition, the membership is one agent's use of it. A project is a unit of work, projected in a GitHub-backed Program onto an epic issue, though the epic is only how the project appears on one tracker.

Each agent's ULID id is separate from its display name, so reusing a name can never merge two agents' histories; a partial-unique index on active names enforces that. The Store holds only recorded facts. The authored configuration stays in the repository and is read when it is needed, pinned to one commit per tick by the Runtime (§V).

An agent's state, the answer to “where are we”, is computed rather than stored, and this part runs today. PAM reads live forge signals (the pull request's state, its CI result, its review decision, whether it is a draft) and combines them with a ledger of per-requirement entries, each checked against the live commit. An entry is done, stale, asserted, or open. The classification is non-monotonic: a rebase can move a done entry back to stale, so PAM reports “done as of <commit>” and never a bare “done”. Wiring the current Oracle stage into this view is part of finishing the ADA fold-in (issue #14).

Runtime & Actions

The Runtime watches a Program's event sources, decides what is actionable, and dispatches Actions, its plugins. An Action is a trigger (an event or a schedule) plus a handler (deliver to an existing agent, spawn one, run a skill, or run a script), on the model of a GitHub Actions workflow. The Runtime delivers to an agent that already exists rather than starting a fresh container each time.

Why not a workflow runner. The obvious home for “watch the forge, react” is a workflow runner, and it does not fit, for two structural reasons. A stock ephemeral runner cannot keep an agent alive: a run gets a container, does one thing, and is destroyed, while an ADA agent must survive from the moment a pull request opens until it merges, holding a worktree and accumulated context. And some work cannot run in that model at all, such as a scheduled check against infrastructure with no runners or a secrets-bound host. The honest form of the claim is “why not an ephemeral runner”, not GitHub Actions in particular. A self-hosted runner can hold a worktree and secrets, and a durable-execution service can survive across a pull request's life, so each solves part of the problem. What is left, a persistent agent that holds context across many events, is what the Runtime provides as the local and durable bridge.

Delivery fires once per material change. The Runtime's first duty in correctness is to avoid re-firing an Action on every poll. A pull request open for days should trigger its Action once, not every sixty seconds. Each Action is keyed on a hash of its id, the subject it acts on, and a signature of the signals it cares about, with volatile parts normalized away so that “idle 4.3h” and “idle 4.6h” count as one state. The Store keeps the last signature and fire time, and the Action fires only when the signature is new or has changed, subject to a per-Action cooldown. The guarantee is at-least-once delivery with idempotent handlers. It is not exactly-once. This decision core, with its dedup and cooldown and a dispatch interface, runs today in dry-run mode.

Live delivery is designed and health-aware (forthcoming). Delivering to an agent that already exists assumes the agent is alive, and a long-running Claude session can lose context or stop. So before delivering, the Runtime is to check the agent's health. It delivers to an alive or idle agent with Claude's native SendMessage. It respawns a dead agent from its stored launch spec and then delivers. For unknown health it refuses and surfaces the case rather than deliver into a void. Because SendMessage is native, PAM carries no messaging stack of its own: the Runtime says “send message M to agent A”, and an injected adapter resolves A to its live session and sends. The poll loop and this live dispatch are the next build step behind the gate (issue #21).

Reads are consistent within a tick. The configuration is read live and never cached, and “live” needs a fixed point, so at the start of each tick the Runtime resolves the Program config to one commit and reads everything at that commit for the whole tick. An edit made in the middle of a tick cannot split one decision across two versions.

Program config & sharing

A Program's authored configuration lives in the repository under .pam/: the roles, the skills, the Oracle checks for this project, the Actions, and the label-to-state map. It is text, version-controlled, and reviewed through the same pull requests as the code. That is also how PAM keeps its documentation and code from drifting apart, a rule the project enforces: the docs and the code that makes them true land in the same change. The intended entry point is pam init, run once in a repository the way you run git init; it is the next thing being built (issue #43). Today the authored config is scaffolded through the existing pam program commands.

Sharing a Program is cloning its repository. Because the authored half lives in .pam/ and the recorded half stays in ~/.pam/, a teammate who clones the repository gets the setup and none of your running state, and the local database is regenerated rather than committed. There is no separate bundle to publish and no central index to register against. An earlier design had both, and they were dropped in favor of config-in-the-repository. A central community marketplace, a pam registry on the model of a package index, is a possible later addition and is deferred. It would have its own trust questions to answer first, since installing another person's Program means running their Actions and scripts on your hosts.

Boundaries & invariants

One tool. PAM is one tool, so the earlier question of whether ADA should be a separate dependency or folded in is closed: ADA is a built-in part of pam, and the Oracle ships with it.

The no-tmux invariant. pip install pam works on a machine with no tmux. PAM never imports cmux; cmux integrates with PAM, not the other way round. Cmux's remaining value is workspaces and keeping agents alive, while native SendMessage handles agent-to-agent messaging. The Runtime's decision core is tmux-free and runs dry-run by default, and real dispatch goes through the cmux seam. A test keeps the no-import rule green, and cmux is out of scope for now.

Hierarchy is organizational, not an execution path. The reports_to edge is an org-chart label. PAM does not route live work from agent to agent through many hops, because information is lost at each hop. Runtime delegation stays within two levels.

Discussion & open questions

This section separates what is settled from what is open. The consolidation to one tool settled several earlier questions. ADA is folded into pam rather than kept as a separate repository. A Program's config lives in the repository's .pam/, so sharing is a clone and the publish, install, and central-registry machinery was dropped. The motivation is argued against any ephemeral runner, not GitHub Actions alone. The split between a project and its forge epic is settled: the core models the unit of work.

What is open is mostly what is not yet built. pam init and the .pam/ layout are next (#43). Finishing ADA means curating its process, skills, and doctrine into a short set rather than the earlier monolith, and wiring its Oracle stage into the computed state (#44, #14). The Runtime's poll loop and its gated live dispatch are next, and three defaults stay unset: the cooldown value, the policy for unknown health, and where the cmux seam lives. A Program-level shared Knowledge Base is planned (#34). If a community marketplace is ever built, it needs a trust model for running another person's Actions. Issue #35 tracks the open design questions.
