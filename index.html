PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

PAM (Project Agentic Management) is one tool for running AI agents against real software projects. You add it to a git repository by running pam init, the way you run git init, and the repository becomes agent-workable. PAM comes with a few primitive agent types. The central one is ADA, an atomic agent that takes a single issue, develops it in an isolated worktree against a ledger of what must become true, carries it to a pull request a human reviews and merges, and then stops. A second type, the Project Lead, owns a whole Project rather than a single issue, and a generic type covers everything else. For a team, PAM adds the coordination and a Runtime around a fleet of these agents. PAM stores its state the way git does: a Program's authored configuration lives in the repository under .pam/, committed and shared, while each developer's recorded state lives in ~/.pam/ and stays on their machine. This paper gives the key concepts, ADA's method and the problem its Oracle solves, the pieces of PAM and how they fit, the storage architecture, a worked example of the command line, and the parts still to come.

Key concepts

PAM is one tool, pam. You run it in a git repository and that repository becomes a Program: a project PAM can run agents against. Open Library is one such Program. Lenny, Petabox, and PAM itself are others, and nothing in the core is specific to Open Library. PAM ships a small set of primitive agent types. ADA is the atomic development agent, and it is the piece nearly every project wants, because every project needs an agent that can take one unit of work to a quality pull request and then stop. A Project Lead owns a Project and coordinates the agents working it. A generic type covers any other role. Work is organized into Projects, and the Runtime is the layer that watches the project's issues and pull requests and hands work to agents that are already running. Figure 1 shows how the pieces sit together, including the split between what lives in the repository and what lives on your machine.

The arrow between the Runtime and the forge runs from the Runtime to the forge on purpose: the Runtime polls, pulling changes on its own schedule, and the results come back on the same request. The direction could be reversed only if the forge pushed events, through webhooks or a workflow, but then a durable, long-lived agent would have nothing holding it to receive them, and you would not need the Runtime at all. PAM polls precisely because a persistent agent cannot depend on the forge reaching it. That is the same reason an ephemeral runner does not fit this work.

ADA and its method

ADA is at the heart of PAM. Its defining idea is the unit it owns. An ADA agent owns a single issue and the pull request that resolves it, as a pair, and it runs a disciplined process over that pair from start to finish. This is the contrast with a Project Lead, which owns a whole Project, the epic that groups many issues. ADA works small on purpose: one issue, one pull request, one agent, carried end to end. Figure 2 shows the process.

The process. ADA starts by posting a ledger: one line for each thing that must become true, written in the issue's own terms as a behaviour rather than a task. It develops in its own worktree, writing a failing test first and watching it fail for the expected reason before making it pass, and it adds a regression test for every defect it hits, written before the fix. It opens a draft pull request early, because work that stays invisible until it is finished is work nobody can help with. It then tests in the real environment, which is not the same as the test suite passing, and sorts every claim into what it actually ran and what it only read. Before marking the work ready it gets an adversarial review from a subagent that inherits none of its context, so the reviewer is blind to the author's intent, and every finding is either fixed with a test or rebutted with evidence. It never merges; a human does that.

The Oracle, and the problem it solves

The failure the Oracle addresses is an agent that is about to stop without noticing what is left, for example one that wrote tests for code it never actually ran. The Oracle is a subconscious, not a supervisor. It does not drive the agent, sequence it, or approve it. When the agent is about to stop, the Oracle surfaces at most one thing it may have missed, and the agent decides what to do with it. Overruling it costs one recorded line, which lets good reasoning be told from drift and lets the Oracle learn which of its promptings are noise. The rule that matters most is that its silence is not approval: nothing firing includes the case where nothing could fire, so a check that stayed quiet and a check that could not run look the same.

Why the method holds

A few principles run underneath all of this, carried from the practice that produced ADA. Progress is not monotonic: a rebase un-does a test that passed, and a moving base un-does a green build, so ADA never reports that something is simply done. It reports the state as of a specific commit. Silence is indistinguishable from finished, so before an agent goes quiet it says what it did, what it could not verify, and what is now blocked and on whom. An honest gap beats a confident wrong claim, because an honest gap costs an hour while a confident wrong claim costs a week and is repeated by everyone downstream. These are not style preferences. They are what lets one human trust the output of many agents at once.

How PAM works

With ADA in view, here are the pieces of PAM and how they relate.

Programs are repositories. A Program is a git repository you have run pam init in. It owns its code and its authored configuration. Running agents against a project and version-controlling how you run them are the same act.

Teams are the agent types plus their assignment. The agent types are the primitives (ADA, Project Lead, and Generic), and a membership assigns a specific agent to a Program with a type and a reporting line. An agent is first-class and independent of any Program, so the same agent can join more than one. A membership is the binding; the type is the definition.

Note, a gap to reconcile. The shipped seed roles are program_lead, division_lead, ada_agent, and agent. “Project Lead” is the umbrella for the two lead roles (the Program Lead owns the Program, a Division or Project Lead owns a set of Projects), and “Generic” is agent. The paper uses Mek's three-type framing while the code uses four seed roles; this is filed on #35 to reconcile the names rather than paper over them.

Projects are the units of work. A Project is a unit of work owned by a Project Lead and worked by ADA agents on its parts. In a GitHub-backed Program a Project is projected onto an epic issue, with its pieces as sub-issues, but the epic is only how the Project appears on one tracker. The concept is the unit of work; the epic is its projection.

The Runtime drives the fleet. The Runtime watches a Program's issues and pull requests, decides what is actionable, and dispatches through Actions. An Action is a trigger (an event or a schedule) plus a handler (deliver to an existing agent, spawn one, run a skill, or run a script). It delivers to an agent that already exists rather than starting a fresh container each time. The Runtime is covered in Section IV and its own design note; what matters here is that it is the piece that turns a change on the forge into work for an agent.

Program configuration is per project. Each Program carries its own configuration: the Oracle checks for this project, the ADA setup, the roles and labels, the Actions, and the label-to-state map. It is authored text in the repository, so it is reviewed through the same pull requests as the code.

Architecture: where state lives

PAM splits its state the way git does, and for the same reason. One half is authored and shared and belongs with the code. The other half is recorded, specific to one machine, and must not be shared. Keeping a cache of the authored half is what rots, so PAM does not cache it: it reads the authored config live from the repository when it needs it. Figure 3 shows the split.

In the repository: .pam/. pam init creates .pam/ in the repository, with program.toml inside it. That file is the Program's authored config: the roles beyond the built-ins, the label-to-state map, the Oracle defaults, and the ADA setup. You commit .pam/ with your code, and a teammate who clones the repository gets the Program. As a Program grows it can carry more authored text here, such as its skills and its Actions.

On your machine: ~/.pam/. This is per-developer recorded state, never shared, like ~/.gitconfig. It holds the Store, a single SQLite database (pam.db) that records which Programs you have, your agents, their memberships and roles, the Projects, and each agent's phase. It also holds one home directory per agent under agents/<id>/, which keeps that agent's identity file, its sessions, its ledger, its received messages, and its cq.

cq, concretely. cq is an ADA agent's own issue tracker, one small SQLite queue per agent for the work it is tracking for itself, separate from the forge issues it is assigned. It lives inside the agent's home under ~/.pam/, on the recorded side, because it is local working state that means nothing to a teammate. An agent reads and writes its own cq; no one else's.

The Store is recorded fact, so it can always be rebuilt and is never committed to git. Each agent also carries a full relaunch spec in the Store, because resuming a session by id alone does not restore the model, settings, and other flags it was started with, and an agent brought back without them is subtly different from the one that stopped.

Using PAM

The command surface is pam. The flow below runs today. You make a repository agent-workable, register the people who will work it, define a Project, put an agent on a piece of it, and then read state back.

pip install -e .

cd ~/Projects/openlibrary
pam init                         # create .pam/ here; register the Program in ~/.pam

# add the people who work this Program
pam agent onboard tags-lead --program openlibrary --role division_lead
pam agent onboard ada-13842 --program openlibrary --role ada_agent --reports-to tags-lead

# a Project (a forge epic) and an ADA agent on one of its sub-issues
pam project add "Tags" --program openlibrary --lead tags-lead --epic 13755 --year 2026
pam project assign "Tags" --agent ada-13842 --sub 13842 --by tags-lead

# read state back
pam status                       # your Programs and their leads
pam agent state ada-13842        # computed work state from forge signals
pam agent ledger ada-13842       # per-requirement ledger: done / stale / asserted / open vs HEAD
pam project state "Tags"         # the epic rollup and each agent's state

A name that is already live cannot be onboarded again, because reusing a name must never merge two agents' histories; retire the old one first with pam agent retire. The state commands read live signals from the forge and the agent's ledger and report the position against the current commit, never as a bare percentage. Other commands fill out the same surface: pam role ls, pam agent ls, pam membership ls, pam team add, and pam program show.

Where this is going

Several pieces are designed and not yet built, and the paper marks them as such rather than describing them as working. The Runtime's poll loop and its live dispatch are next (#21): the decision core, with its dedup and per-action cooldown so a pull request open for days fires an Action once rather than every poll, runs today in dry-run, while delivery to a live agent is gated. Live delivery is health-aware by design: it delivers to an alive agent with Claude's native SendMessage, respawns a dead agent from its stored relaunch spec, and refuses on unknown health rather than deliver into a void. Finishing ADA means curating its process, skills, and doctrine into a short set rather than the earlier large manual (#44), and wiring its current Oracle stage into the computed state (#14). A Program-level shared Knowledge Base, the store of what a team has learned that an agent reads before a task and writes back to after, is planned (#34).

The registry, later. Sharing a Program today is cloning its repository, since the authored half lives in .pam/ and the recorded half stays in ~/.pam/. An earlier design added a shareable bundle and a central index to publish and install Programs; both were dropped in favour of config-in-the-repository. A central community marketplace, a pam registry on the model of a package index, is a possible later addition and is deferred. It carries its own trust question, because installing another person's Program means running their Actions and scripts on your hosts, and that question has to be answered before such a thing ships.

The design rests on principles that should outlast any particular feature. An agent owns one unit of work and carries it whole. Position is reported against a commit, because it is not monotonic. Silence is treated as a failure to report, not as success. An honest gap is cheaper than a confident wrong claim. The system is built so that one person can trust the work of many agents, and every choice above is in service of that.
