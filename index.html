PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

This paper describes PAM (Project Agentic Management), a general-purpose system for running a fleet of long-lived AI agents against real software projects. PAM is the successor to ADA, the automation pipeline that maintains Open Library. ADA demonstrated that constrained, transparent, human-gated LLM agents can carry high-volume work from a filed issue to a merged change; but its machinery was entangled with Open Library specifics and with one terminal multiplexer. PAM factors the durable parts out into three layers: a Registry (a local, SQLite-backed record of Programs, first-class agents, memberships, roles, and projects, keyed by stable ULID identity); a Runtime (an event→action execution layer — watch event sources, decide, dispatch to durable agents — whose plugins are Actions, modeled on GitHub Actions but able to deliver work to an agent that already exists rather than spawning an ephemeral container); and shareable Programs (pam‑{program} git repos — the Docker-Hub/PyPI model for agent teams — each bundling repos, a shared Knowledge Base, an Oracle verification definition, roles, and Actions). Open Library becomes one Program among many. We motivate the design against the founding constraint — why a workflow runner cannot keep an expensive, worktree-holding agent alive across a PR's lifetime — and state the invariants (notably pip install pam on a host with no tmux) that keep the layers from re-merging.

Overview

PAM runs a fleet of long-lived AI agents against real projects. An operator configures a Program — a project, its repos, its team, its tooling — and PAM keeps those agents fed from the events that matter (a new issue, a PR, a review request, a scheduled check) while tracking who the agents are and what they are doing. Open Library is one Program; Lenny, Petabox, and PAM itself are others. Nothing in the core is Open-Library-specific.

From ADA to PAM

What carries over. Much of ADA's philosophy is retained deliberately: atomic agents (one unit of work, carried end to end), the shared Knowledge Base read before a task and written back after, isolated worktrees so half-finished changes never collide, human-gated merges, and the event→action model. PAM keeps the shape of the work ADA proved; it changes where the machinery lives.

What changes. cq (per-agent work tracking), identity/lifecycle, and the action system move into PAM — the first two into the Registry, the action system into the Runtime. cmux reduces to a multiplexer: in ADA it carried session mechanics, identity, and an inbox; in PAM it is only a tool for multiplexing Claude sessions/workspaces. Claude's native SendMessage replaces the old cmux-send messaging, so inter-agent messaging no longer needs a bespoke socket layer as its primitive.

Architecture

PAM is three layers. (1) The Registry — local SQLite in ~/.pam/, the identity-and-policy store of recorded state. (2) The Runtime — the execution layer that watches event sources, decides what is actionable, and dispatches to durable agents; its plugins are Actions. (3) The Program — a configured instance's authored setup (repos, Knowledge Base, Oracle definition, roles, Actions, config), version-controlled as text in a pam‑{program} repo. The layers are held apart by a single invariant (§VII) and by the authored-vs-recorded split that runs through all three.

The registry

The registry records Programs (which own repos), agents (first-class and Program-independent, with a stable ULID id and a reusable display name), memberships (an agent joins a Program with a role and a reporting line), roles (a seedable catalog), and projects (units of work; a project is a forge epic). Identity is a surrogate ULID, separate from the mutable display name, so reusing a name can never merge two agents' histories — enforced by a partial-unique index on active names. Only recorded facts live in SQLite; the authored config is read live from the repo and never cached.

Runtime & Actions

The Runtime is the reason PAM exists. It watches event sources (polls or subscribes to the forge), decides what is actionable, and dispatches Actions — its plugins, modeled on GitHub Actions: a trigger (on: an event, or a schedule) plus a handler (deliver-to-an-existing-agent, spawn, run-a-skill, run-a-script).

Why not GitHub Actions — the founding constraint. A workflow run is ephemeral: it gets a container, does a thing, and is destroyed. A development agent is the opposite — expensive to set up, holding a worktree and accumulated context, and it must survive from the moment a PR opens until it merges. An Action cannot keep an agent alive; the most it carries across runs is a pointer to an environment it cannot hold. And some work (a scheduled check against infrastructure with no runners, a secrets-bound host, a private config repo) cannot run in an Action at all. So the event source is remote and execution must be local and durable; the Runtime is the bridge, and it messages an agent that already exists rather than starting one. Where an Action works, use an Action.

Programs, Oracle & the Knowledge Base

A Program is a configured instance (Open Library, Lenny, PAM-itself). It bundles its repos, a shared Knowledge Base, an Oracle definition, roles, Actions, and config. Two of these deserve their own names. The Knowledge Base (KB) is a Program-level shared knowledge repo (Open Library's is ol-kb) — authored, shared, read before a task and written back after; it is the direct descendant of ADA's Obsidian vault (see issue #34). The Oracle is the verification layer: a Program's Oracle definition — an ordered set of guard states — is how PAM determines an agent's state for a Project (which guard is the first unsatisfied one). Oracle is external, pinned, and not vendored (§VII).

Programs are shareable. An operator should be able to hand a whole team setup to someone else. PAM makes a Program's config serializable to a git repo (e.g. pam‑openlibrary) — the Docker-Hub/PyPI model for agent teams. Shared (text, in the repo): roles and Division-Lead templates, skills, the Oracle definition, Actions, recipes, the label→state map, the KB, and the pinned versions of PAM/ADA/Oracle it builds on. Never shared (local, in SQLite): which agents exist, their sessions, who claimed which issue — recorded state, useless or misleading to a teammate whose work hasn't started. Clone → pam program install → bind local values → staff it with your agents. A .db is never checked into git; it is regenerated on install.

Boundaries & invariants

Fold-in vs. depend-on. A tool useful on its own stays its own repo and PAM depends on it, pinned (Oracle, a general verification runner); a tool that only makes sense inside PAM folds in (ADA becomes a built-in agent-type + a progress renderer + an onboarding recipe).

The no-tmux invariant. pip install pam && pam program add … works on a machine with no tmux. PAM never imports cmux; cmux uses PAM. The Runtime's decision core is tmux-free and runs in dry-run; delivery goes through the cmux multiplexer seam. A test keeps this green.

Hierarchy is organizational, not a runtime delegation path. The reports_to edge is an org-chart label; PAM does not build multi-hop real-time agent-to-agent delegation (deep hierarchies lose information at each boundary). Runtime delegation stays ≤2 levels.
