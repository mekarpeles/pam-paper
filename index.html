PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

PAM (Project Agentic Management) is a general-purpose system for running a fleet of long-lived AI agents against real software projects. An agent in PAM follows the ADA model, where ADA stands for Atomic Agent: it takes one unit of work, builds in an isolated git worktree, reads and writes a shared Knowledge Base, and carries the work to a change that a human reviews and merges. PAM is the system around those agents. It records who they are, holds the configuration for every project it manages, and drives the agents from the events that matter. PAM has three layers. The Store is a local SQLite database of the agents, Programs, roles, and projects on one machine. The Runtime watches a project's issues and pull requests, decides what needs doing, and dispatches work to agents that are already running. A Program is one configured instance, such as Open Library, packaged as a git repository that bundles its code repos, its Knowledge Base, its Oracle (the definition of when work is done), and its roles, skills, and Actions, and published to a central Registry by pull request. This paper describes the model, the three layers, and the constraints that shape them, including why an ephemeral workflow runner cannot do this work and why the core installs and runs without a terminal multiplexer.

Overview

PAM runs a fleet of long-lived AI agents against real projects. You configure a Program (a project, its repositories, its team, and its tooling), and PAM keeps the agents fed from the events that matter (a new issue, a pull request, a review request, a scheduled check) and tracks what each agent is doing. Open Library is one Program. Lenny, Petabox, and PAM itself are others. Nothing in the core is specific to Open Library.

The model

The agent. Start with one agent. PAM runs its agents on the ADA model (Atomic Agent). An agent takes a single unit of work, usually one issue or one pull request, and stays with it from start to finish. It works in an isolated git worktree, a private checkout of the repository, so unfinished changes from different agents never collide. Before it starts, it reads the project's Knowledge Base, the shared store of what the team has already learned, and it writes back what it finds. It never merges its own work. A human reviews every change and performs the merge. These conventions come from ADA, the agent system that maintains Open Library; the ADA paper [1] describes them in full.

Knowing when work is done. An agent has to know when a task is finished, and that judgment is the Oracle. A Program defines its Oracle as an ordered set of guard states, for example “the branch builds”, then “the tests pass”, then “a reviewer has approved”. PAM reads the first guard the work has not yet satisfied and reports it as the agent's current state. The Oracle is a separate, pinned tool rather than a part of PAM, because it is useful on its own.

How work reaches an agent. Work reaches an agent through an Action. An Action is a small declarative rule with two parts: a trigger (an event, such as “a subtask was assigned”, or a schedule) and a handler (deliver a message to an agent, spawn a new agent, run a skill, or run a script). Skills and Actions are different things. A Skill is a capability an agent uses while it works. An Action is the rule that starts the work.

The Program and the three layers. PAM organizes all of this around a Program. A Program is one configured instance: its repositories, its Knowledge Base, its Oracle definition, its roles, its skills, and its Actions. Open Library is a Program; Lenny and Petabox are others, and PAM can run itself as a Program. Three layers make a Program work. The Store is a local SQLite database that records what exists on one machine: the installed Programs, the agents, their roles, and the projects. The Runtime watches each Program's issues and pull requests and dispatches work to agents through Actions. A Program's configuration is text in a git repository (named pam‑{program}, such as pam‑openlibrary), so anyone can publish and share it; the central Registry is the public index of those published Programs, and you register a Program by opening a pull request against it. One naming point, since an earlier draft got it wrong: in this paper Store always means the local database, and Registry always means the central public index. The rest of the paper takes the three layers in turn: the Store (§III), the Runtime (§IV), and Programs with their Oracle and Knowledge Base (§V).

The Store

The Store is the local SQLite database on one machine. It records Programs (each owns one or more repositories), agents (first-class and independent of any Program, each with a stable ULID id and a reusable display name), roles (a seedable catalog of definitions that carry permissions), and memberships (the binding that joins an agent to a Program with a role and a reporting line). A role and a membership are different: the role is the definition, the membership is one agent's use of it. A project is a unit of work. In a GitHub-backed Program a project is projected onto an epic issue, but the epic is only how the project appears on one tracker. The core models the unit of work itself, so a Program on a different tracker fits the same model.

Each agent's ULID id is separate from its display name, so reusing a name can never merge two agents' histories; a partial-unique index on active names enforces that. The Store holds only recorded facts. The authored configuration stays in the Program repository and is read at the moment it is needed (the Runtime pins that read to one commit per tick, §IV).

An agent's state, the answer to “where are we”, is computed rather than stored. PAM keeps no percentage. Its renderer reads live forge signals (the pull request's state, its CI result, its review decision, whether it is a draft) and combines them with a ledger of per-requirement entries, each checked against the live commit. An entry is done, stale, asserted, or open. The classification is non-monotonic: a rebase can move a done entry back to stale, so PAM reports “done as of <commit>” and not a bare “done”. The last input, the current Oracle stage, arrives with the ADA fold-in (issue #14).

Runtime & Actions

The Runtime is the reason PAM exists. It watches a Program's event sources, decides what is actionable, and dispatches Actions, its plugins. An Action is a trigger (an event or a schedule) plus a handler (deliver to an existing agent, spawn, run a skill, or run a script), on the model of a GitHub Actions workflow.

Why not GitHub Actions. The obvious place to run “watch GitHub, react to a change” is GitHub Actions. It does not fit here, for two structural reasons. First, a workflow run is ephemeral. It gets a container, does one thing, and is destroyed. A PAM agent is expensive to set up and holds a worktree, a running stack, and accumulated context, and it has to stay alive from the moment a pull request opens until it merges. A workflow cannot keep that agent alive; the most it can carry between runs is a session id, a pointer to an environment it has already thrown away. Second, some work cannot run in a workflow at all: a scheduled check against infrastructure that has no runners, a secrets-bound host, or a private configuration repository. So the event source is remote and the execution has to be local and durable. The Runtime is that local, durable layer. Where a workflow does fit, use a workflow.

Framing note (to settle with Mek). State the claim at the right level. The real question is whether any ephemeral runner can do this work; GitHub Actions is only one example. A self-hosted runner can hold a worktree and secrets. A durable-execution engine such as Temporal, or a long-running service with a job queue, can survive across a pull request's life. What PAM needs is a persistent, context-holding agent that lives across many events, and that requirement is what the motivation should argue.

Delivery fires once per material change. The Runtime's first duty in correctness is to avoid re-firing an Action on every poll. A pull request that stays open for days should trigger its Action once, not every sixty seconds. Each Action is keyed on a hash of its id, the subject it acts on, and a signature of the signals it cares about. Volatile parts of the signature are normalized away, so “idle 4.3h” and “idle 4.6h” count as one state. The Store keeps the last signature and fire time for each Action and subject, and the Action fires only when that signature is new or has changed, subject to a per-Action cooldown. The guarantee is at-least-once delivery with idempotent handlers, so a repeated delivery is safe. It is not exactly-once.

Delivery is health-gated. “Deliver to an agent that already exists” assumes the agent is alive, and a long-running Claude session is not guaranteed to be: it can lose context or stop. So the Runtime checks an agent's health before it delivers. If the agent is alive or idle, the Runtime delivers the message with Claude's native SendMessage. If the agent is dead, the Runtime respawns it from its stored launch spec (with the session id and working directory) and then delivers. If the health is unknown, the Runtime refuses and surfaces the case rather than delivering into a void. Because SendMessage is native, PAM carries no messaging stack of its own: the Runtime says “send message M to agent A”, and an injected adapter resolves A to its live session and sends. Address resolution, health checks, and respawning sit below that adapter, in the harness, which keeps the Runtime's decision core free of any terminal-multiplexer dependency.

Reads are consistent within a tick. The configuration is read live and never cached, but “live” needs a fixed point. At the start of each tick the Runtime resolves the Program bundle to one commit and reads every Action, role, Oracle definition, and label map at that commit for the whole tick. An edit made in the middle of a tick cannot split one decision across two versions of the configuration.

Programs, Oracle & the Knowledge Base

A Program is one configured instance, such as Open Library. It bundles its repositories, a shared Knowledge Base, an Oracle definition, roles, skills, and Actions. Two pieces need a word of their own. The Knowledge Base is the Program's shared knowledge repository (Open Library's is ol-kb). An agent reads it before a task and writes back to it after, and it is the successor to the Obsidian vault ADA used (issue #34). The Oracle is the verification definition introduced in §II: an ordered set of guard states whose first unsatisfied member is the agent's current state. The Oracle is a separate, pinned dependency and is not vendored into PAM (§VI).

A Program is shareable. A Program's configuration is text, so it can be handed to someone else. PAM serializes it to a git repository such as pam‑openlibrary, on the model of a package registry for agent teams. The shared half is the text in the repository: roles and lead templates, skills, the Oracle definition, Actions, recipes, the label-to-state map, the Knowledge Base, and the pinned versions of PAM, ADA, and Oracle it builds on. The private half stays in local SQLite: which agents exist, their sessions, and who claimed which issue. That recorded state belongs to one machine and would mislead a teammate whose own work has not started. The flow has three steps. Publish pushes the pam‑{program} repository. Register adds the Program to the central Registry with a pull request against the official PAM repository. Install (pam program install) clones it, binds local values such as checkout paths and the bot account, and generates fresh local rows. A database file is never committed to git; it is regenerated on install.

Security gate (tracked, issue #20). Installing another person's Program runs that Program's Actions and scripts on your hosts under your bot account. That is an arbitrary-code-execution and supply-chain surface, the same one any package index carries. Before “clone and install” is advertised, publish and install need a trust and review model, and a way to supply secrets that never writes them to the Store or the logs.

Boundaries & invariants

Fold-in versus depend-on. A tool that is useful on its own keeps its own repository, and PAM depends on it at a pinned version; the Oracle is such a tool. A tool that only makes sense inside PAM folds in; ADA folds in as a built-in agent type, a progress renderer, and an onboarding recipe.

The no-tmux invariant. pip install pam and pam program add work on a machine with no tmux. PAM never imports cmux; cmux imports PAM, never the other way round. The Runtime's decision core is tmux-free and runs in dry-run mode, and real delivery goes out through the cmux adapter. A test keeps this property green.

Hierarchy is organizational, not an execution path. The reports_to edge is an org-chart label. PAM does not route live work from agent to agent through many hops, because information is lost at each hop. Runtime delegation stays within two levels.

Discussion & open questions

This section separates what is settled from what is open, so the paper argues rather than advertises. Several risks raised in early review are now answered in the Runtime design. Delivery fires once per material change (§IV). Liveness is health-gated, with respawn and rehydrate. Native SendMessage removes the need for a separate messaging stack. Each tick pins the configuration to one commit. The earlier confusion between a project and its forge epic is settled: the core models the unit of work and projects it onto an epic (§III).

Three questions stay open. The publish and install security gate (§V) is not built. The motivation (§IV) should be argued against any ephemeral runner, addressing self-hosted runners and durable-execution engines directly, which waits on Mek's decision. And three Runtime defaults are unset: the cooldown value, the policy for unknown health, and where the cmux adapter lives. Issue #35 tracks the current list.
