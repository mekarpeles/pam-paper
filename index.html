PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

PAM (Project Agentic Management) is a way to design, structure, and share a standard agentic project-management workflow for your projects. You add it to a git repository with pam init, the way you run git init, and the repository gains a configured team of AI agents that carry work from an issue to a reviewed pull request. The core of PAM is ADA, the Atomic Development Agent: it owns one issue and its pull request as a pair, develops in an isolated worktree against a ledger of what must become true, and stops when the only step left is a human merge. Around ADA, PAM defines a small set of pieces: a project tracking system for issues, a development system for pull requests, a Knowledge Base, and a Runtime that watches for work and dispatches it to agents that already exist. PAM stores its state the way git does: authored configuration lives in the repository under .pam/, shared through commits, while each developer's recorded state lives in ~/.pam/. This paper gives the model, the philosophy, each piece in turn, how to use the command line, and a case study of Open Library.

What is PAM

PAM is a way to design, structure, and share a standard agentic project-management workflow for your projects. You add it to a git repository, and the repository gains a configured team of agents that take work from your issue tracker to reviewed pull requests. Open Library is one project run this way. Lenny, Petabox, and PAM itself are others, and nothing in the core is specific to Open Library.

It helps to separate two kinds of thing. The architectural components are how state is stored and run: a local Store, the split between what lives in the repository and what lives on your machine, and a Runtime that watches for work. The functional pieces are what you configure for a project: a project tracking system for issues, a development system for pull requests, a Knowledge Base, the Runtime, and ADA, the agent that does the work. There is one tool, pam; ADA ships inside it. Figure 1 shows how the pieces fit.

Philosophy

A few principles hold the design together, carried from the practice that produced ADA. An agent owns one unit of work and carries it whole, from the issue to a reviewed pull request. Progress is not monotonic: a rebase un-does a test that passed, and a moving base un-does a green build, so an agent reports its position against a specific commit rather than claiming something is simply done. Silence is indistinguishable from finished, so before an agent goes quiet it says what it did, what it could not verify, and what is now blocked and on whom. An honest gap beats a confident wrong claim, because an honest gap costs an hour while a confident wrong claim costs a week and is repeated by everyone downstream.

Two structural principles sit underneath those. State is split the way git splits it: authored configuration is shared in the repository, and recorded state stays on each machine, so no stale cache of the authored half can drift from the truth. And documentation stays in sync with code: a change to how the system behaves and the documentation that describes it land together, because an agent that reads a stale document acts on it. The aim of all of this is that one person can trust the work of many agents at once.

The Program

Every Program starts with a git repository and the pam command line. You run pam init in a repository, the way you run git init, and PAM creates .pam/ in the repository and registers the Program in your local store. A Program is the repository plus its .pam/ configuration. It owns the roles, the Projects, and the rest of the authored setup. (pam init and the .pam/ layout are shipped.)

PAM splits its state the way git does. The authored half lives in the repository and is shared through commits; the recorded half stays on each developer's machine. Figure 2 shows the split.

In the repository, .pam/program.toml holds the roles, the labels, the tracking and development system configuration, and the Oracle and ADA setup. On your machine, ~/.pam/ holds the Store, a single SQLite database (pam.db) that records your Programs, agents, their memberships and roles, the Projects, and each agent's phase, plus one home directory per agent. A teammate who clones the repository gets the setup and none of your running state. (The Store, agents, memberships, roles, and Projects are shipped.)

The Forge

The Forge is what powers a Program's work. It is an umbrella over two configurable systems: a project tracking system, where Issues and Projects live, and a development system, where pull requests and review live. At a minimum a Program needs these two, Issues and PRs.

The two systems are configured separately, and they can be one product or two. GitHub does both, so one product can cover the Forge. Or they can differ, for example Jira for Issues and GitHub for pull requests. Tracking system examples are Jira and GitHub Issues; when the repository's remote does not imply a forge such as GitHub, PAM falls back to local cq as the default tracking system. Development system examples are GitHub, GitLab, and Gerrit. An ADA agent owns an Issue in the tracking system and a PR in the development system as a pair, so one unit of work spans both. Figure 3 shows the two systems side by side.

Docs-first note. The two-system split is the intended model. The shipped schema has a single programs.tracker field plus repos, and the forge adapter reads GitHub signals today. Splitting the configuration into a tracking system and a development system, and the local-cq default, are filed on #35 so the code reconciles to the model.

Projects

A Project is a unit of work: an epic that groups issues. Projects and their issues live in the tracking system, and a Division Lead owns and manages a Project. In a GitHub-backed Program a Project is projected onto an epic issue, with its pieces as sub-issues; the epic is how the Project appears in that system, and the concept is the unit of work itself. (Projects and their membership are shipped; pam project add, assign, and state run today.)

A Program does not have to build its tracking and development adapters from scratch. The intended model lets it fetch what it needs as Forge plugins from a registry, for example a GitHub plugin, a Jira plugin, or a GitLab plugin. The registry and the plugin model are forward-looking; sharing a Program today is cloning its repository.

The team and roles

A Program is worked by a team, also called the fleet: the agents staffed on it. An agent is first-class and independent of any one Program, and it joins a Program through a membership that gives it a role and a reporting line. PAM ships four roles, kept distinct on purpose.

ADA, the Atomic Development Agent

ADA is the core of PAM, the agent that does the work. It owns a single issue and the pull request that resolves it, as a pair, and runs a disciplined process over that pair. It posts a ledger: one line for each thing that must become true, written in the issue's own terms as a behaviour rather than a task. It develops in its own worktree, writing a failing test first and watching it fail for the expected reason before making it pass, and adds a regression test for every defect it hits, written before the fix. It opens a draft pull request early, so the work is visible while in progress. It then tests in the real environment, which is not the same as the suite passing, and sorts every claim into what it ran and what it only read. Before marking the work ready it gets an adversarial review from a subagent that inherits none of its context. It never merges; a human does that. Figure 4 shows the process.

The Oracle. The Oracle augments the agent's stop hook and prevents premature idling. It is a subconscious, not a supervisor: it does not drive the agent or approve it. When the agent is about to stop, the Oracle surfaces at most one thing it may have missed, for example tests written for code that was never actually run, and the agent decides what to do with it. Its silence is not approval, because nothing firing includes the case where nothing could fire, so a check that stayed quiet and a check that could not run look the same.

cq. cq is an ADA agent's own issue queue, one small SQLite tracker per agent for the work it is tracking for itself, kept in the agent's home under ~/.pam/. It is also the default local project tracking system when the repository's remote does not imply a forge. (The agent home is shipped; folding cq into PAM and using it as the default tracker is forward-looking.)

Division Leads

A Division Lead manages Projects and epics. The Lead owns a set of Projects, breaks them into issues for ADA agents, and unblocks those agents as a consultant. Reporting is organizational, not an execution path: the reporting edge is an org-chart label, and PAM does not route live work from agent to agent through many hops.

Program Lead

The Program Lead is a meta role. It owns the Program itself: it keeps the Program's documentation current and unblocks Division Leads where it can. It tends the shared setup rather than any single Project.

Generic

The generic role is the catch-all for a team member that is not one of the above, so a Program can staff a role PAM does not name without inventing a type.

Note. These four roles are the shipped seed roles (program_lead, division_lead, ada_agent, agent) and the paper keeps them distinct rather than collapsing the two lead roles into one. A Program can define its own roles on top of these.

The Knowledge Base

The Knowledge Base is a Program-level shared store of what the team has learned, for humans and agents alike. An agent reads it before a task and writes back to it after, and every agent contributes, so a lesson learned once does not have to be learned again. Open Library's is ol-kb. (A first-class Knowledge Base is planned, tracked on #34.)

The suggested format is Obsidian-style: plain markdown notes linked with wikilinks, the [[note]] style, so it reads for a person and an agent alike and needs no special tooling. A Program can also install a shared Knowledge Base from the registry, the way it would a Forge plugin; the installed base lives at the Program level as kb. (The registry is forward-looking, but this is the intended mechanism.)

The Runtime

The Runtime is the event watcher for the Forge, similar in spirit to the GitHub Actions API, with one difference that is the reason PAM exists: it can keep a durable agent alive across many events. It polls the tracking system for work and reads pull-request and CI state from the development system, decides what is actionable, and dispatches to an agent that already exists rather than starting a fresh container each time. Its plugins are Actions: a trigger (an event or a schedule) plus a handler (deliver to an agent, spawn one, run a skill, or run a script).

The Runtime fires an Action once per material change, not once per poll, so a pull request open for days triggers its Action once rather than every minute. It does this with a dedup key over the signals an Action cares about and a per-Action cooldown. (The decision core, with dedup, cooldown, and a dispatch interface, runs today in dry-run. The poll loop and live, health-gated dispatch are the next build step, tracked on #21.) Figure 5 shows the event-to-action cycle.

The arrow from the Runtime to the tracking system runs outward on purpose: the Runtime polls, pulling changes on its own schedule, and the results come back on the same request. The direction could be reversed only if those systems pushed events, through webhooks or a workflow, but then a durable, long-lived agent would have nothing holding it to receive them, and you would not need the Runtime at all. PAM polls precisely because a persistent agent cannot depend on a remote system reaching it. That is the same reason an ephemeral runner does not fit this work.

Using PAM

The pam command line

The command line manages the Program and the team. It is structured as pam <noun> <verb>: a Program, an agent, a membership, a Project. The flow below runs today. You make a repository agent-workable, register the people who work it, define a Project, put an agent on a piece of it, and read state back.

cd ~/Projects/openlibrary
pam init                         # create .pam/ here; register the Program in ~/.pam

pam agent onboard ol-lead  --program openlibrary --role program_lead
pam agent onboard tags-lead --program openlibrary --role division_lead --reports-to ol-lead
pam agent onboard ada-13842 --program openlibrary --role ada_agent    --reports-to tags-lead

pam project add "Tags" --program openlibrary --lead tags-lead --epic 13755 --year 2026
pam project assign "Tags" --agent ada-13842 --sub 13842 --by tags-lead

pam status                       # your Programs and their leads
pam agent state ada-13842        # computed work state from pull-request and CI signals
pam agent ledger ada-13842       # per-requirement ledger: done / stale / asserted / open vs HEAD
pam project state "Tags"         # the epic rollup and each agent's state

A name that is already live cannot be onboarded again, because reusing a name must never merge two agents' histories; retire the old one first with pam agent retire. The state commands read live pull-request, CI, and ledger signals and report the position against the current commit, never as a bare percentage.

cmux workspaces

cmux integrates with PAM for workspaces and for keeping agents alive, while Claude's native SendMessage handles agent-to-agent messaging. The relationship is one-way: PAM never imports cmux, so pip install pam works on a machine with no tmux, and a test keeps that rule green. The Runtime's decision core is tmux-free and runs dry-run by default; real dispatch goes through the cmux seam. (The cmux integration is out of scope for now; the no-import rule is shipped and tested.)

The Dashboard

A dashboard over the Store and the fleet, showing Programs, Projects, and where each agent is, is planned. (Forward-looking; not yet built.)

Case study: Open Library

Open Library is a large open-source library catalog maintained by a small staff, and it is the first project run as a PAM Program. Its earlier automation, ADA, is described in a companion paper [1]; PAM generalizes that work so any project can adopt it. As a Program, Open Library uses GitHub for both the tracking system and the development system, so one product covers the Forge. A Program Lead tends the shared setup and the documentation. Division Leads own the epics, for example an import pipeline or an internationalization effort, and break them into issues. ADA agents take those issues to reviewed pull requests, reading and writing the shared Knowledge Base, ol-kb, as they go. A human reviews and merges. This is the shape PAM is built to make ordinary: a small group of people directing a larger fleet of agents, each carrying one unit of work, with the configuration shared in the repository for anyone to pick up. (Open Library is the reference instance; the fuller write-up of its operation lives in the ADA paper and will grow here as the Program runs on PAM.)
