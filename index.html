PAM: Project Agentic Management

Michael E. Karpeles (Mek), Internet Archive  <mek@archive.org>

Internal engineering note · 2026 · working draft

Abstract

This paper describes PAM (Project Agentic Management), a general-purpose system for running a fleet of long-lived AI agents against real software projects. PAM is the successor to ADA, the automation pipeline that maintains Open Library. ADA demonstrated that constrained, transparent, human-gated LLM agents can carry high-volume work from a filed issue to a merged change; but its machinery was entangled with Open Library specifics and with one terminal multiplexer. PAM factors the durable parts out into three layers: a Store (a local, SQLite-backed record of installed Programs, first-class agents, memberships, roles, and projects, keyed by stable ULID identity); a Runtime (an event→action execution layer — watch event sources, decide, dispatch to durable agents — whose plugins are Actions, modeled on GitHub Actions but able to deliver work to an agent that already exists rather than spawning an ephemeral container); and shareable Programs (pam‑{program} git repos — the Docker-Hub/PyPI model for agent teams — each bundling repos, a shared Knowledge Base, an Oracle verification definition, roles, skills, and Actions, published into a central Registry by pull request). Open Library becomes one Program among many. We motivate the design against the founding constraint — why a workflow runner cannot keep an expensive, worktree-holding agent alive across a PR's lifetime — and state the invariants (notably pip install pam on a host with no tmux) that keep the layers from re-merging.

Overview

PAM runs a fleet of long-lived AI agents against real projects. An operator configures a Program — a project, its repos, its team, its tooling — and PAM keeps those agents fed from the events that matter (a new issue, a PR, a review request, a scheduled check) while tracking who the agents are and what they are doing. Open Library is one Program; Lenny, Petabox, and PAM itself are others. Nothing in the core is Open-Library-specific.

From ADA to PAM

What carries over. Much of ADA's philosophy is retained deliberately: atomic agents (one unit of work, carried end to end), the shared Knowledge Base read before a task and written back after, isolated worktrees so half-finished changes never collide, human-gated merges, and the event→action model. PAM keeps the shape of the work ADA proved; it changes where the machinery lives.

What changes. cq (per-agent work tracking), identity/lifecycle, and the action system move into PAM — the first two into the Store, the action system into the Runtime. cmux reduces to a multiplexer: in ADA it carried session mechanics, identity, and an inbox; in PAM it is only a tool for multiplexing Claude sessions/workspaces. Claude's native SendMessage replaces the old cmux-send messaging, so inter-agent messaging no longer needs a bespoke socket layer as its primitive.

Architecture

PAM is three layers. (1) The Store — local SQLite in ~/.pam/, the identity-and-policy record of this machine's state. (2) The Runtime — the execution layer that watches event sources, decides what is actionable, and dispatches to durable agents; its plugins are Actions. (3) The Program — a configured instance's authored setup (repos, Knowledge Base, Oracle definition, roles, skills, Actions, config), version-controlled as text in a pam‑{program} repo and published into a central Registry. The layers are held apart by a single invariant (§VII) and by the authored-vs-recorded split that runs through all three. A naming note worth stating once, since an earlier draft got it wrong: the local SQLite is the Store; Registry is reserved for the central, public index of published Programs (§VI).

The Store

The Store is this machine's local SQLite record. It holds Programs (which own repos), agents (first-class and Program-independent, with a stable ULID id and a reusable display name), roles (a seedable catalog of definitions carrying permissions), and memberships (the binding that joins an agent to a Program with a role and a reporting line — the Role is the definition, the Membership is the use of it). A project is a unit of work; in a GitHub-backed Program it is projected onto a forge epic. Keeping the concept separate from its forge projection is deliberate: the general core models a unit of work, and “epic” is how that unit is rendered on one tracker, not what it is.

Identity is a surrogate ULID, separate from the mutable display name, so reusing a name can never merge two agents' histories — enforced by a partial-unique index on active names. Only recorded facts live in the Store; the authored config is read live from the Program repo and never cached (the Runtime pins that read at one SHA per tick — §V).

An agent's state (“where are we”) is computed, never a stored percentage. PAM's shipped renderer composes a coarse category from live forge signals (PR state, CI conclusion, review decision, draft) with a ledger of per-requirement entries bucketed against live HEAD — done / stale / asserted / open, deliberately non-monotonic (a rebase un-does done; PAM prints only “done as of <sha>”). The one remaining input, the current Oracle stage, arrives with the ADA fold-in.

Runtime & Actions

The Runtime is the reason PAM exists. It watches event sources (polls or subscribes to the forge), decides what is actionable, and dispatches Actions — its plugins, modeled on GitHub Actions: a trigger (on: an event, or a schedule) plus a handler (deliver-to-an-existing-agent, spawn, run-a-skill, run-a-script). An Action is distinct from a Skill: a Skill is a capability an agent uses; an Action is a trigger that invokes work (and may, through the run-a-skill handler, invoke a Skill).

Why not GitHub Actions — the founding constraint. A workflow run is ephemeral: it gets a container, does a thing, and is destroyed. A development agent is the opposite — expensive to set up, holding a worktree and accumulated context, and it must survive from the moment a PR opens until it merges. An Action cannot keep an agent alive; the most it carries across runs is a pointer to an environment it cannot hold. And some work (a scheduled check against infrastructure with no runners, a secrets-bound host, a private config repo) cannot run in an Action at all. So the event source is remote and execution must be local and durable; the Runtime is the bridge, and it messages an agent that already exists rather than starting one. Where an Action works, use an Action.

Honest framing (to settle). The sharp form of the claim is not “why not GitHub Actions” but “why not an ephemeral runner.” The motivation section should steelman the real alternatives: a self-hosted runner can hold a worktree and secrets, and a durable-execution engine (e.g. Temporal) or a long-running service with a job queue can survive across a PR's life. The defensible distinction is persistence of an expensive, context-holding agent across many events, not persistence of a runner — and that distinction, not “Actions are ephemeral,” is what should carry the argument.

Delivery semantics — fire once per material state-change. The Runtime's first correctness duty is to not re-fire an action every poll tick: a PR open for days must trigger its action once, not every 60 seconds. The design keys each action on a dedup hash of (action id, subject ref, state signature) — the normalized signals the action cares about, with volatile bits stripped (so “idle 4.3h” and “idle 4.6h” are the same signature). The Store records the last signature, fire time, and count; an action fires only when the signature is new or changed, honoring a per-action cooldown — reusing the heartbeat new/repeat/changed/cooldown verdicts. The contract is at-least-once with idempotent handlers (deliver carries a dedup marker; spawn checks for no running session first), not exactly-once.

Health-gated delivery. “Deliver to an agent that already exists” assumes a liveness long Claude sessions do not guarantee — they compact, degrade, or die. So the Runtime checks health before delivering: alive/idle → deliver via native SendMessage; dead → respawn-and-rehydrate from the agent's full stored launch_spec (plus session id and cwd) and then deliver; unknown → refuse and surface, never silently void. Because Claude now carries native SendMessage, the Runtime does not re-implement ADA's socket/mux delivery stack; it emits “send message M to agent A,” and the injected dispatch adapter resolves A to a live session and sends. What remains below the adapter — address resolution, health, (re)spawn — is a harness concern, keeping the decision core tmux-free and dry-run-able.

Read-consistency. Authored config is read live and never cached, but each Runtime tick pins the Program bundle at a single resolved HEAD SHA and reads every action, role, oracle definition, and label map at that SHA for the whole tick — so a mid-tick edit can never split one decision across two versions.

Programs, Oracle & the Knowledge Base

A Program is a configured instance (Open Library, Lenny, PAM-itself). It bundles its repos, a shared Knowledge Base, an Oracle definition, roles, Actions, and config. Two of these deserve their own names. The Knowledge Base (KB) is a Program-level shared knowledge repo (Open Library's is ol-kb) — authored, shared, read before a task and written back after; it is the direct descendant of ADA's Obsidian vault (see issue #34). The Oracle is the verification layer: a Program's Oracle definition — an ordered set of guard states — is how PAM determines an agent's state for a Project (which guard is the first unsatisfied one). Oracle is external, pinned, and not vendored (§VII).

Programs are shareable. An operator should be able to hand a whole team setup to someone else. PAM makes a Program's config serializable to a git repo (e.g. pam‑openlibrary) — the Docker-Hub/PyPI model for agent teams. Shared (text, in the repo): roles and Division-Lead templates, Skills, the Oracle definition, Actions, recipes, the label→state map, the KB, and the pinned versions of PAM/ADA/Oracle it builds on. The flow is publish (push the pam-{program} repo) → register (open a PR that adds the Program to the central Registry in the official PAM repo — git-native, like a package index) → install (others pam program install by name, bind local values, and staff it with their own agents). Never shared (local, in SQLite): which agents exist, their sessions, who claimed which issue — recorded state, useless or misleading to a teammate whose work hasn't started. Clone → pam program install → bind local values → staff it with your agents. A .db is never checked into git; it is regenerated on install.

Security gate (tracked). Installing someone else's Program runs its Actions and run-a-script handlers against your hosts and your bot account — an arbitrary-code execution and supply-chain surface the package-index analogy brings with it. Publish/install must carry a trust and review model, and a secrets-injection path that never lands credentials in the Store or logs, before “clone and install” is advertised. This is a gate on the sharing epic, not an afterthought for the paper to omit.

Boundaries & invariants

Fold-in vs. depend-on. A tool useful on its own stays its own repo and PAM depends on it, pinned (Oracle, a general verification runner); a tool that only makes sense inside PAM folds in (ADA becomes a built-in agent-type + a progress renderer + an onboarding recipe).

The no-tmux invariant. pip install pam && pam program add … works on a machine with no tmux. PAM never imports cmux; cmux uses PAM. The Runtime's decision core is tmux-free and runs in dry-run; delivery goes through the cmux multiplexer seam. A test keeps this green.

Hierarchy is organizational, not a runtime delegation path. The reports_to edge is an org-chart label; PAM does not build multi-hop real-time agent-to-agent delegation (deep hierarchies lose information at each boundary). Runtime delegation stays ≤2 levels.

Discussion & open questions

This section records where the design is settled and where it is still open, so the paper argues honestly rather than advertising. Several early risks are now resolved by design in docs/runtime-design.md: delivery fires once per material state-change (dedup hash + cooldown over the heartbeat verdicts, §V); liveness is health-gated with respawn-and-rehydrate; native SendMessage removes the bespoke delivery stack; and each tick pins the bundle at one SHA. The “project vs. forge epic” conflation is resolved: the core models a unit of work and projects it onto an epic (§IV).

Still open. (1) The publish/install security gate (§VI) — trust, review, and secrets injection — is unbuilt. (2) The motivation framing should move from “why not GitHub Actions” to “why not an ephemeral runner,” steelmanning self-hosted runners and durable-execution engines (§V, pending Mek's call). (3) Runtime defaults from the design doc: the cooldown value (4h vs. per-action), the unknown-health policy (refuse-and-surface vs. a bounded retry), and where the cmux dispatch adapter lives. The companion thread on #35 tracks the live list.
